# 3. 通信协议与仿真生命周期

## 3.1 总体流程

```text
UE启动Python
  → gRPC连接与握手
  → reset_property（等待UE点击开始，获取静态编组）
  → reset_obs（获取首帧动态态势）
  → 创建红蓝算法
  → [构造阵营视图 → 每实体选一个动作 → 发送frame → 接收下一帧 → 奖励/训练]
  → EndEpisode
  → 下一回合重新reset并刷新动态UID，或结束会话
```

准备阶段会持续重试，因为 UE 尚未点击开始或正在重建实体时可能暂时不返回完整数据。正式 `step` 超时后不会自动重发：动作可能已经被 UE 执行，盲目重发会产生重复效果。

## 3.2 首帧编组

`reset_property` 的 `propertyArr` 建立本回合实体清单。`team` 表示阵营（0 红、1 蓝）；框架为每方战斗实体分配 `team_index`，它是本方 `state.agents` 的动作行号；UE 原始 `indexInTeam` 表示当前上级 UID。框架把 `BaseCommander_C` 单独放入 `commanders`。UE 的动态 `uId` 可能在新回合变化，算法不得跨回合缓存 UID；需要稳定分工时应使用本方 Agent 的 `team_index`。

`reset_obs` 返回 `dataArr` 和 `dataGlobal`。框架按 UID 把动态数据对齐到本回合内部实体清单，读取回合号、训练标志、战略目标和首帧态势，然后创建算法。不能依赖 `dataArr` 的原始数组位置识别实体。

## 3.3 每帧动作

每个阵营必须按 `state.agents` 顺序，为每个战斗实体返回一个且仅一个逻辑动作。普通动作被编码进 `StringActions`；`ChangeParentAction` 因 UE 接口不同而通过独立 gRPC 调用，但仍占用该实体本帧唯一动作槽，常规字符串位置只发送 `Idle` 协议占位。

同一实体不能在一帧同时移动、攻击或指派上级。重复在后续帧选择 `ChangeParentAction` 会重复调用 UE，框架不跨帧去重。

## 3.4 转移和训练

收到下一帧后，运行器生成双方隔离视图，过滤事件，调用 `calculate_reward`，再形成 `LearningTransition`。强化学习算法的 `train_on_transition` 决定是否保存经验和更新模型；规则算法默认忽略训练转移。

终局时先处理最后一条转移，再调用 `on_episode_end(episode)`。全部回合结束时调用 `on_simulation_end()` 并关闭 gRPC。UE 首帧 `dataGlobal.rSVD1` 中的训练标志决定当前会话是训练还是比赛；比赛模式应贪心推理，不写经验、不更新网络、不覆盖模型。

## 3.5 gRPC 通道分别做什么

| 通道 | 方向 | 用途 | 是否等待回包 |
|---|---|---|---|
| `handshake` | 双向 | 确认客户端身份和协议版本 | 是 |
| `prepare` | 双向 | `reset_property`、`reset_obs` | 是，可安全重试 |
| `frame` | 双向 | 发送本帧动作并取得下一帧 | 是，超时不重发 |
| `custom` | Python→UE | `end_unreal_engine` 等控制通知 | 否 |
| `special` | 双向独立接口 | 当前为 `ChangeActorParent` | 是 |

接收任务只是同一个 asyncio 事件循环中的异步任务，不是操作系统工作线程，也不会注册守护进程。

`prepare.type` 不能按请求和回包对称理解：Python 请求会填写 `reset_property` 或 `reset_obs`，但当前 UE 的 prepare 回包可能不回填同名 `type`，有效数据仍在 `prepare.data` 的 JSON 中。框架保持 prepare 请求串行，并按 prepare 通道接收当前等待的回包，再由 JSON 中的 `propertyArr`、`dataArr`、`dataGlobal` 等实际内容校验结果；不能因为回包 `prepare.type` 为空就丢弃有效数据。

## 3.6 JSON 外层结构示例

准备请求由框架生成，典型结构为：

```json
{
  "valid": true,
  "DataCmd": "reset_property",
  "NumAgents": 0,
  "TimeStepMax": 200,
  "TimeDilation": 1.0,
  "FrameRate": 60.0,
  "TimeStep": 0,
  "Actions": null
}
```

正式动作帧典型结构为：

```json
{
  "valid": true,
  "DataCmd": "step",
  "TimeStep": 12,
  "Actions": null,
  "StringActions": [
    "ActionSet2::Moving;+X;101",
    "ActionSet2::Idle;N/A;102"
  ],
  "RSVD1": "None"
}
```

`StringActions` 中每条字符串末尾都带有执行者的本回合动态 UID，UE 按该 UID 定位执行实体，不使用字符串在数组中的下标定位单位。因此该数组不要求复刻 `propertyArr` 的原始红蓝交错顺序。Python 框架当前按内部实体清单合并红蓝动作，并为每条字符串编码正确的执行者 UID。

这里需要区分两种“顺序”：选手返回的动作序列仍必须与本方 `state.agents` 逐行对应，因为框架依靠动作行确定应当写入哪个执行者 UID；完成 UID 编码后，发送给 UE 的 `StringActions` 数组位置本身不再承担实体身份语义。检查协议日志时应核对每条字符串末尾的 executor UID，而不是把同一下标与 `propertyArr` 强行比较。

UE 回包的主要结构为：

```json
{
  "valid": true,
  "dataArr": [{"uId": 101, "agentAlive": true}],
  "dataGlobal": {
    "timeCnt": 13,
    "episodeDone": false,
    "events": [],
    "keyObjArr": []
  }
}
```

示例只展示骨架，不能据此假定其他字段一定存在。DEBUG 模式的 `protocol.jsonl` 才是当前场景和当前 UE 版本的原始依据。

## 3.7 为什么准备请求能重试而正式帧不能

`reset_property` 和 `reset_obs` 是读取准备状态，重复查询不会让实体重复执行战术动作。`frame` 则可能已经被 UE 接收并执行，只是回包因超时没有到达。如果 Python 再发送一次，同一动作可能执行两次，状态步号也可能错位，所以框架选择立即报错并保留日志，由开发者联合 UE 日志定位。

prepare 超时重试时也不要自行增加“回包必须回显请求 type”的条件。实跑已经确认 UE 可以返回有效 `propertyArr`，同时 protobuf `prepare.type` 为空；判断 reset 是否成功应以 JSON 内容及必需字段为准。

## 3.8 回合边界需要注意什么

- 新回合重新取得 property 和 observation，UID 可以全部改变。
- 算法对象、网络、优化器和经验池不会重新创建。
- 本方 Agent 的 `team_index` 由新编组按队内顺序建立，用于动作行和稳定分工；`indexInTeam` 仍表示当前上级 UID。
- 最后一帧先计算奖励和训练，之后才触发回合结束钩子。
- 整场退出时会尽力发送结束通知；UE 已主动断流时出现关闭警告不一定代表前面仿真失败。
