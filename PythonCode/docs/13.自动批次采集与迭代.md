# 自动批次采集与离线迭代

批次工具把真实比赛、运行配置、代码提交和模型 SHA 绑定在一起。界面导航由桌面控制端处理；后台监督器只启动和管理自己持有的 Python 子进程，不向未观察到的界面盲点，也不按进程名批量关闭应用。

## 启动顺序

1. 确认只有一个 `C:\CSSIM\Server\Server\Server.exe` 管理服务器，后台运行；打开 CSSIM 客户端并登录。
2. 单席位 → 第十届比赛场景 → 比赛想定：10 局、1 倍速，其他保持不变。
3. 红方选择 `N_Rest Ssured_red`，不勾选红方 Bot；蓝方不使用模型，勾选蓝方 Bot（平台 MatchBOT）。
4. 算法配置：1 线程、CPU、500 步、0.5 单步时间、随机种子 10098；勾选启动 PyCharm、启动渲染、保存配置，不共享 Reward。
5. 训练模式进入关卡。检查 PyCharm 已启动；未启动则保留失败记录后重新开始。关卡显示正在与 Python 建立连接时，才启动下面的后台主函数。不要同时点 PyCharm 的 Run，以免启动第二份 Python。
6. 后台已启动且连接状态正常后，再点击对局播放按钮。

UE 会重新生成 `cssim_25vs25.jsonc`，并可能删除 `hybrid_iql` 配置。不能凭上一轮磁盘文件推断本次运行模式。以下工具会保留生成文件，另外生成批次配置，显式绑定已发布模型。

## 后台命令

在仓库根目录执行，示例批次 ID 必须每次更换：

```powershell
$py = 'C:\CSSIM\Client\Data\AlgData\PythonEnv\python.exe'
$batch = '20261031-b001'
& $py tools\prepare_training_config.py C:\CSSIM\Client\Data\AlgData\PythonCode\TaskConfig\cssim\cssim_25vs25.jsonc --out "logs\autotrain-configs\$batch.json"
& $py tools\batch_training.py prepare --config "logs\autotrain-configs\$batch.json" --batch-id $batch
& $py tools\autotrain_runtime.py "logs\autotrain\$batch\manifest.json"
```

第三条会阻塞到本批 Python 退出，自动化端应使用隐藏后台进程启动它并重定向自己的输出。它默认保留至少 10 GB 磁盘空间，连续 10 分钟无统计进展或整批超过 360 分钟时终止自己启动的 Python，并记录具体原因。它不会关闭别的 Python、PyCharm、服务器或客户端进程。

运行中可读取 `logs/autotrain/<批次>/supervisor-status.json`，或调用：

```powershell
& $py tools\batch_training.py status "logs\autotrain\$batch\manifest.json"
& $py tools\batch_training.py finish "logs\autotrain\$batch\manifest.json"
```

`finish` 仅在全部证据符合时输出 `results/batches/<批次>.json`：UE 的实际场景标记为 `10;1`、十局 reset 都加载指定模型、十个不同回合的 done、十局红蓝终局分数归属明确、Python 实际退出码为零、正常 run_end，以及配置/代码/模型身份一致。总分为终局摧毁分加 `Reward`。日志短暂停写或仅一局有分数不算整批完成。

创建批次时还会联网核验 `origin/main` 与本地提交一致，将核验提交与时间写入清单；运行中的状态轮询不访问远端。框架在跨局重置和最后结束通知之后，最多等待 10 秒收齐该局两条终局成绩，再关闭接收连接；缺失、重复或无效成绩不会按正常完成处理。

在批次目录创建 `STOP` 文件，可请求监督器结束本批 Python。停止或崩溃会标成未完成，保留原日志。重试使用新批次 ID，不覆盖原目录。客户端正常退出可能来自 Python 的结束命令，应先检查完整成绩，不能一律误判崩溃。

## 迭代学习

每批结束后保存并推送比赛记录。先保持当前模型收集不同对手部署的真实样本；候选训练不直接改变正在运行的模型。

```powershell
& $py tools\train_batch_candidate.py --batches "results\batches\$batch.json" --sources <历史协议1> <历史协议2> <更多历史协议> --candidate-id "${batch}-candidate"
```

该命令重新核验已完成批次的协议 SHA 和每局成绩，结合明确指定的历史来源，建立独立训练/验证/测试批次，调用离线 IQL 提取器和训练器，生成 `logs/autotrain-candidates/<候选>/candidate.json`、`review.json` 和训练报告。已核验新比赛的代码提交会写入数据清单，未知历史版本保持未知。失败的未完成批次不经此命令自动训练；其中已完成局可在单独审核后作为历史来源导入。

来源按显式指定的历史顺序、随后新批次顺序排列；最后两个有效会话分别留作验证和测试，前面的会话才参与梯度训练。因此只加入第一批新十局时，这十局用于测试，不能宣称模型已从这十局学习。加入至少三个新批次后，最早的新批次才可能进入训练集；具体角色以 `split_sessions` 和数据清单为准。

候选应先通过 `evaluate_target_iql.py` 接入检查，再由迭代控制端审查并将模型与报告复制进仓库，执行 `tools/publish.ps1`。必须先验证、提交、推送并确认远端，再同步两端。新模型的对照比赛才用于判断得分是否改善；离线一致率不能当成分数。差的候选可保留记录并回退已发布基线，不能为凑迭代次数强行推广。

## 桌面恢复与状态

安装 `tools/requirements-autotrain.txt` 后，可使用连续总控：

```powershell
& $py tools\cssim_campaign.py run --campaign-id <唯一名称> --recipe tools\cssim_flow.json --gate-after-success --train-candidate
& $py tools\cssim_campaign.py status logs\campaigns\<唯一名称>
& $py tools\cssim_campaign.py stop logs\campaigns\<唯一名称>
```

`run` 默认没有批次数上限。首次应由隐藏进程启动总控并重定向控制台日志；客户端是用户要求显示的交互窗口。可用 `--server-pid <已确认PID>` 显式复用已有管理器，总控核验其路径和创建时间，批间只关闭客户端并等待专用对局服务器退出，保留常驻管理器。它不会请求或绕过 Windows 管理员权限。

总控先验证 GitHub 与部署文件，再执行图像校验的界面步骤，绑定实际平台配置，等待后台握手和 reset 请求，最后按播放键。每次尝试都有独立目录，连续三次失败停止重试；未知画面和其它未归属的 Python 进程会停下，不会猜测点击或批量杀进程。界面校准为 1600×900，配置时会占用鼠标与前台，人工操作会干扰识别。

成功报告单独提交、推送并核验远端；候选训练只生成待审文件。`--gate-after-success` 在每批结束后等待迭代审查。审查端确认继续基线，或者先完成候选检查、发布与部署后，再运行 `cssim_campaign.py release <campaign目录>`。不得在正在采集时替换算法或模型。

桌面控制端每次观察当前窗口后再执行下一步，遇到登录、弹窗、分辨率或界面变化重新识别；不复用过期坐标。崩溃后先保存本批部分成绩与真实退出原因，再关闭经路径和进程身份核验的 CSSIM 实例，重启下一尝试。连续失败应停止重启风暴并报告原因。

这些后端工具的测试通过不等于整条桌面流程已经实测跑通。首次发布时应明确记录 UI 控制是否可用、首批是否已开始，以及有多少局真实完成。
