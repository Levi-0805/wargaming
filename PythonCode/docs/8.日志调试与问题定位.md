# 8. 日志、调试与问题定位

## 8.1 日志文件

每次启动在 `logs/YYYYMMDD_HHMMSS/` 创建独立目录：

| 文件 | 内容 |
|---|---|
| `runtime.log` | 连接、算法加载、回合切换、异常和训练摘要；自动轮转 |
| `simulation.jsonl` | reset 与每一步结构化记录 |
| `protocol.jsonl` | 仅 DEBUG 生成，保存完整 gRPC JSON 收发报文 |

DEBUG 下 `simulation.jsonl` 还包含 roster、实体位置、动作索引、最终动作字符串、战略目标、动作回显和特殊动作结果。INFO 会去掉大字段，适合长时间训练。

## 8.2 日志级别

设置来源按优先级为：命令行 `--log-level`、环境变量 `CSSIM_LOG_LEVEL`、TaskConfig 的 `GlobalConfig.log_level`、默认 DEBUG。协议字段取证时使用 DEBUG，100 回合等长训练建议用 INFO。

## 8.3 排查顺序

1. 查看 `runtime.log` 是否完成连接、reset 和红蓝算法加载。
2. 查看 reset 记录中的 roster、commanders、key_objects 和 team_state_counts。
3. 查看 `action_indices` 与 `action_strings`，确认每个实体均有一个动作，并核对每条字符串末尾的执行者 UID。
4. 指派上级时查看 `special_commands` 的 UID、success 和 message；普通动作位应为 Idle。
5. 对比实体前后位置、生命值、事件和终局字段，不只依赖 `previousAction`。
6. 若 Python 发送格式正确、UE 无解析错误但没有物理效果，应转向 UE 实体动作实现定位。

## 8.4 常见问题

- `ModuleNotFoundError: TeamAlg...`：配置指向的队伍目录不存在、未同步或缺少 `__init__.py`。
- 一直等待准备：UE 尚未点击开始、未启用 Python 或正在重建回合实体。
- UE 已返回 `propertyArr` 但 Python 仍一直等待：确认客户端没有强制匹配回包的 protobuf `prepare.type`。当前 UE 回包可能不回填该字段，应接收 prepare 通道的当前串行回包并校验 JSON 必需字段。
- 正式帧超时：查看同时间段 UE 日志和最后一条 protocol 记录；框架不会自动重发。
- 新回合动作指向错误：算法缓存了上一回合 UID，应重新从 `TeamState` 查询。
- 怀疑动作数组错位：UE 按每条字符串末尾的执行者 UID 定位单位，不要用 `StringActions` 下标与 `propertyArr` 下标直接比较；应检查本回合 UID 是否有效、是否唯一覆盖各战斗实体，以及动作参数中的目标 UID 是否正确。
- 攻击了“自己看不见”的敌人：误用了队伍级 `visible_opponents`；局部攻击用 `perceived_opponents(agent)`。
- 加载模型失败：动作集合签名、网络或特征结构与检查点不一致，应重新训练。

## 8.5 `simulation.jsonl` 怎么读

JSONL 表示“一行一个完整 JSON 对象”。不要把整个文件当作一个 JSON 数组。第一类是回合 reset 记录：

```json
{
  "kind": "reset",
  "episode": 1,
  "training": true,
  "team_state_counts": {"0": {}, "1": {}},
  "action_sets": [],
  "roster": [],
  "commanders": [],
  "key_objects": []
}
```

它回答“本回合实际有哪些实体、指挥员和指挥所”“模型动作维度是多少”“当前是不是训练模式”。每个新回合都应出现一条 reset 记录，因此可以据此确认多回合是否真正重建成功。

roster 中 `team=0/1` 分别表示红/蓝阵营；本方实体的 `team_index` 是该阵营动作行号。若需要确认上级关系，应查看原始协议实体中的 `indexInTeam`，其值是当前上级 UID，不是日志数组下标。

第二类是逐步记录，常用字段包括：

| 字段 | 排查用途 |
|---|---|
| `episode` / `step` | 定位具体帧 |
| `done` / `winner` / `end_reason` | 判断是否终局及原因 |
| `alive` | 红蓝存活数量 |
| `actions` | 本帧各命令数量统计 |
| `action_indices` | 强化学习红蓝动作编号 |
| `action_strings` | Python 实际发送给 UE 的完整动作字符串 |
| `special_commands` | 指派上级等独立接口执行结果 |
| `action_echo` | UE `previousAction` 与发送字符串的辅助比较 |
| `reward_sum` | 红蓝奖励合计 |
| `training_metrics` | loss、epsilon、经验池、更新次数等 |
| `events` | 框架内部记录的本帧 UE 事件，用于联调取证 |
| `entities` | DEBUG 下的逐实体位置、速度、血量和存活状态 |
| `key_objects` | DEBUG 下的目标位置、有效性和生命值 |

`action_echo.mismatch_count` 只能作为诊断线索。由于部分 UE 版本不更新 `previousAction`，不能单凭 mismatch 判定动作失败。

日志用于平台维护，因此可以记录比选手态势更完整的调试信息；算法的 `calculate_reward` 只会收到按本阵营己方和可见敌方过滤后的事件。选手不能通过读取运行日志来参与在线决策。

## 8.6 `protocol.jsonl` 怎么读

每一行包含：

```json
{
  "direction": "python_to_ue",
  "channel": "frame",
  "type": "step",
  "payload": {"DataCmd": "step", "StringActions": []}
}
```

- `direction`：`python_to_ue` 或 `ue_to_python`。
- `channel`：handshake、prepare、frame、custom 或 special。
- `type`：reset_property、reset_obs、step、ChangeActorParent 等诊断标签。对于已配对的 prepare 回包，日志可沿用当前请求类型；它不证明 UE 的 protobuf 回包实际回显了同名 `prepare.type`。
- `payload`：解码后的原始 JSON；无法解码时保留字符串。

验证底层语义时，应按同一启动目录、相邻行和相同 channel 配对请求与回包。不要把上一次实验的 protocol 文件与本次 UE 日志混在一起。

普通动作字符串的最后一个分号字段是执行者 UID，例如 `ActionSet2::Moving;+Y;456` 表示让本回合 UID 456 的实体移动。攻击字符串中前一个 UID 是目标、最后一个 UID 是执行者。UE 按这些 UID 解析，不要求 `StringActions` 与 `propertyArr` 具有相同数组顺序。

## 8.7 动作执行的三层判断

一次动作应分别回答三个问题：

1. Python 是否生成正确对象和最终字符串？查看 `action_indices`、`action_strings` 或 `special_commands`。
2. UE 是否收到并成功解析？查看 `protocol.jsonl` 和相同时间段 UE 日志。
3. 实体是否产生预期物理效果？比较连续帧的 `entities`、事件和目标状态。

第一层失败通常是选手算法或 Python 参数问题；第二层失败是协议或 UE 解析问题；前两层成功而第三层失败，通常需要 UE 端开发者检查该实体类型的动作实现。

## 8.8 多回合卡住的定位方法

1. 找到最后一条 `done=true`，确认第二回合是否已经写完终局转移。
2. 查看其后是否出现下一条 `kind=reset`。
3. 没有 reset 时，在 runtime 中查 `等待 UE 开始仿真`，并在 UE 日志确认是否重建实体和发送 prepare 回包。
4. 已有 reset 但没有 step 时，确认红蓝算法是否在 `build_observation`、`select_actions` 或规则 `decide` 抛错。
5. 已发 frame 但没有回包时，使用最后一条 `python_to_ue/frame` 和 UE 同时间日志定位；不要手工重发该帧。

## 8.9 提交问题时应提供什么

- Python 本次运行的完整日志子目录，而不是只截最后一行。
- UE 同一时间段日志。
- 实际 TaskConfig。
- 使用的红蓝 TeamAlg ID、规则/强化学习模式和回合数。
- 出问题的 episode、step、agent UID 和预期行为。
- 是否能够稳定复现，以及最小复现算法。

日志可能包含场景和队伍信息，对外发送前应按比赛要求处理敏感内容。
