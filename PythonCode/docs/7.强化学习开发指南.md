# 7. 强化学习开发指南

## 7.1 选手需要实现什么

强化学习算法直接继承 `ReinforcementAlgorithm`。框架不限定 DQN，选手可以实现 Double DQN、QMIX、PPO 或其他算法，也不需要继承模板中的 `DQNAlgorithm`。

本章的 `team` 表示算法阵营（0 红、1 蓝）；本方 `agent.team_index` 是动作、特征和奖励的队内行号；UE 的 `indexInTeam` 表示当前上级 UID。网络索引只能使用本方 `team_index`，发送目标参数必须使用本回合 `uid`。

接口分成三类：

| 类别 | 接口 | 是否必须覆盖 |
|---|---|---|
| 决策 | `select_actions(observation, action_mask, training)` | 是 |
| 数据 | `build_observation(state)`、`build_action_mask(state)` | 否，有默认实现 |
| 训练 | `calculate_reward(...)`、`train_on_transition(...)` | 否，默认不奖励、不训练 |
| 生命周期 | `on_episode_end(...)`、`on_simulation_end()` | 否 |
| 日志 | `training_metrics()` | 否 |

`act()` 和 `_process_transition()` 是框架的固定编排方法。选手通常不应覆盖或直接调用它们，否则容易绕过动作形状、动作编号和单动作语义校验。

## 7.2 从启动到结束的完整调用顺序

### 7.2.1 算法创建

UE 返回首个回合的 `reset_property` 和 `reset_obs` 后，运行器才创建红蓝算法：

```text
读取首帧编组
  → 创建 AlgorithmContext
  → 读取算法类的 action_definition
  → action_definition.define(context)       自定义固定离散动作顺序
  → ReinforcementAlgorithm.__init__(context)
  → 选手算法 __init__(context, ...)
```

`ActionSetDefinition.define()` 通常只在算法实例创建时调用一次。它适合声明动作槽，不适合读取不断变化的当前态势。需要当前 Agent、目标 UID 或坐标的动作，应声明为 `DiscreteAction.dynamic`，由 resolver 在真正选中该槽时补齐参数。

`AlgorithmContext` 初始包含阵营、本方实体、当前可见敌方、指挥员、设备、算法配置和动作集合。新回合开始后，框架会刷新其中的动态实体对象和 UID；算法不要保存上一回合的实体 UID。

### 7.2.2 首个决策帧

框架先构造安全的 `TeamState`，再按以下顺序调用：

```text
build_action_mask(state)
  → act(state)                              框架方法
      → build_observation(state)
      → select_actions(observation, action_mask, state.training)
      → 校验动作编号数量、范围和可用性
      → RLActionSet.decode(...)             每个Agent解码一个动作
  → 执行被选中的 ChangeParentAction
  → 把普通动作/Idle占位发送给UE
```

`select_actions` 必须返回长度为 `len(state.agents)` 的一维整数序列。第 `i` 个编号只属于 `state.agents[i]`。每个 Agent 每帧只能选择一个编号，因此只能得到一个逻辑动作。

`ChangeParentAction` 虽通过独立 gRPC 接口发送，仍占用该 Agent 的唯一动作槽；常规帧中的 `Idle` 只是协议占位。后续帧再次选中会再次调用 UE，框架不去重。

### 7.2.3 UE 回包后的训练转移

UE 执行动作并返回下一帧后，调用顺序为：

```text
构造 next_state
  → build_action_mask(next_state)
  → calculate_reward(state, next_state, visible_events)
  → 框架创建 EnvironmentTransition
  → _process_transition(...)                框架方法
      → build_observation(next_state)
      → 组装 LearningTransition
      → train_on_transition(transition)
  → training_metrics()
  → 写入 simulation.jsonl
```

`calculate_reward` 和 `train_on_transition` 每个阵营、每个环境转移各调用一次，包括终局转移。终局奖励由运行器在选手奖励之后追加：胜方每个 Agent `+1`，负方每个 Agent `-1`。

`train_on_transition` 在训练模式和比赛模式都会进入。算法必须检查 `transition.state.training` 或自己在动作选择阶段保存的训练状态，决定是否写经验和更新网络。模板 DQN 已完成这项判断。

当前实现会在生成 `next_observation` 时调用一次 `build_observation(next_state)`，下一决策帧又会把同一状态作为当前状态再次编码。因此 `build_observation` 应是无副作用、结果确定的纯转换，不应在其中训练网络、递增 epsilon 或修改经验池。

### 7.2.4 下一决策帧

上一帧的 `next_state` 直接成为下一轮决策的 `state`：

```text
build_observation(state)
  → select_actions(...)
  → 解码并发送动作
  → 接收下一个 next_state
  → 奖励和训练
```

框架重复这一过程，直到 UE 报告 `episodeDone`，收到 `EndEpisode`，或达到最大步数。

### 7.2.5 回合结束和新回合

终局帧仍会先形成完整 `LearningTransition(done=True)` 并调用 `train_on_transition`，随后才调用：

```text
on_episode_end(episode)
```

这里适合做回合统计、衰减回合级参数或按固定周期保存检查点。不要在这里补存终局经验，因为终局经验已经交给 `train_on_transition`。

如果还有下一回合，框架重新执行 `reset_property` 和 `reset_obs`，更新 `AlgorithmContext` 中的实体、指挥员、可见敌方和动作目标数量，但不会重新创建算法实例。网络、优化器和经验池会自然延续；动态 UID 必须从新 `TeamState` 重新获取。

### 7.2.6 整场仿真结束

所有回合完成或运行流程退出时，框架调用：

```text
on_simulation_end()
```

这里适合最终保存模型和释放算法资源。该钩子位于清理流程中，异常退出时也可能被调用，所以实现应允许重复或提前调用，不要假设一定完成了目标回合数。

## 7.3 各接口的输入、输出和副作用

### `build_observation(state) -> Any`

- 输入：本阵营安全视图 `TeamState`。
- 输出：任意选手自定义对象，随后原样传给 `select_actions`，也会存入训练转移。
- 默认：直接返回 `TeamState`；选手通常应覆盖本方法构造自己的模型输入。
- 建议：只做确定性数据转换，不训练、不采样、不修改状态。

### `build_action_mask(state) -> np.ndarray`

- 输出形状：`[Agent数量, 动作数量]`，布尔值。
- `True` 表示当前可选择，`False` 表示不可选择。
- 默认：调用动作集合中每个槽的 `available` 规则。
- 调用时机：每个新阵营视图生成时，在动作选择或下一状态训练数据形成之前。

动作 mask 是 Python 强化学习动作集合的约束，不等于 UE 字段 `availActions`。`select_actions` 应像模板 DQN 一样先把不可用编号的 Q 值屏蔽；框架负责校验动作编号范围和动态目标是否存在，但不会替选手过滤所有战术上无效的动作。

### `select_actions(observation, action_mask, training) -> Sequence[int]`

- 每个决策帧调用一次。
- 返回每个本方战斗实体的离散动作编号。
- `training=True` 时可做 epsilon-greedy 等探索；为 False 时应采用确定性或贪心策略。
- 这里只选择编号，不拼 UE 字符串，也不更新网络。

### `calculate_reward(previous, current, events) -> np.ndarray`

- 输入：动作前后两个安全 `TeamState` 和本阵营可见事件。
- 输出形状：`[Agent数量]`。
- 每条环境转移调用一次，终局也会调用。
- 默认：全零奖励。

### `train_on_transition(transition) -> None`

- 输入：完整 `LearningTransition`。
- 训练会话中负责存经验、采样批次、计算损失、反向传播和更新目标网络。
- 比赛会话中应直接返回，不写经验、不更新或覆盖模型。
- 一个仿真 step 对每个阵营调用一次，不是每个 Agent 分别调用；如果采用单 Agent 经验，可在方法内部按 Agent 行拆分。

### `training_metrics() -> dict[str, int | float]`

- 每个仿真 step 在训练处理之后调用一次。
- 只返回轻量标量，例如 loss、epsilon、更新次数和经验池大小。
- 不应触发训练或模型保存。

## 7.4 `LearningTransition` 字段

| 字段 | 含义 |
|---|---|
| `state` | 动作执行前的安全阵营视图 |
| `observation` | `state` 对应的自定义模型输入 |
| `actions` | 本帧每个 Agent 的动作编号 |
| `reward` | 本帧后每个 Agent 的奖励 |
| `next_state` | UE 回包构成的下一安全阵营视图 |
| `next_observation` | `next_state` 对应的自定义模型输入 |
| `next_action_mask` | 下一状态的动作可用性矩阵 |
| `done` | 是否为本回合终局转移 |

模板 DQN 在 `train_on_transition` 内把队伍级转移按 Agent 行拆成经验。QMIX 等集中训练算法可以保留队伍维度，联合使用所有 Agent 的 observation、action、reward 和 `TeamState` 中公开的队伍信息。

## 7.5 自定义动作集合

继承 `ActionSetDefinition`，在 `define(context)` 中按固定顺序返回 `DiscreteAction`：

- 固定动作使用 `DiscreteAction.fixed(key, action)`；
- 需要当前 Agent、目标 UID 或坐标时使用 `DiscreteAction.dynamic(key, resolver, available)`；
- 将定义对象赋给算法类的 `action_definition`。

动态 resolver 可以返回 `Action` 或 `ChangeParentAction`。模型只选择一个编号，resolver 负责补全该动作需要的参数。动作的名称、顺序、数量或动态目标槽规则发生变化后，旧 Q 网络输出语义已经改变，必须重新训练。

## 7.6 自定义态势和多指挥所

覆盖 `build_observation`，从 `TeamState` 的本方实体、公开敌方、指挥员和战略目标中选择字段并构造模型输入。推荐用 dataclass 明确字段；如果选手使用可变长集合，应自行设计填充或 mask。

模板 DQN 先按稳定 `team_index` 为每个 Agent 分配一个任务目标，再只编码该目标的相对位置和距离；它不会把全部指挥所集合输入示例网络。目标数量变化时会重新分配，但网络输入仍保持固定宽度。需要集中编码全部目标的算法可以自行遍历 `state.key_objects` 并设计对应的集合编码和 mask。

模板中每个 Agent 都产生动作和经验，但所有 Agent 共享一套 Q 网络参数，并不是每个 Agent 各自维护一张网络。选手可以改成按本方 Agent 的 `team_index` 动作行号管理独立网络，也可以实现个体网络加 mixing network 的 QMIX。

## 7.7 训练模式与比赛模式

UE 在首帧 `dataGlobal.rSVD1` 中下发 `training` 标志，最终进入 `state.training` 和 `select_actions(..., training)`。

训练模式通常执行：探索选择、经验存储、批次更新、目标网络同步和检查点保存。比赛模式执行：加载既有模型、贪心选择，不存经验、不反向传播、不保存覆盖模型。

`load_model` 表示启动时是否读取检查点，与 `training` 是两个不同概念。常见组合：

| `load_model` | `training` | 用途 |
|---|---|---|
| False | True | 从头训练 |
| True | True | 续训 |
| True | False | 加载模型进行比赛 |
| False | False | 使用随机初始化模型比赛，通常没有意义 |

用户不能依赖手工修改 UE 生成的 TaskConfig 保存这些选项。模板已经在 `TeamAlg/<队伍ID>/Algorithm/RLAgentAlgorithm.py` 中提供 `AlgorithmConfig`，训练和比赛前修改自己的代码即可：

```python
# 从头训练
mode: str = "reinforcement_learning"
load_model: bool = False

# 继续训练或加载模型参加比赛
mode: str = "reinforcement_learning"
load_model: bool = True
```

TaskConfig 只通过 `AlgorithmConfig_Red/Blue` 指向该对象；没有算法参数覆盖段时，以上代码默认值直接生效。模板检查点路径为 `TeamAlg/<队伍ID>/TrainLogs/dqn_model.pt`。设置 `load_model=True` 前必须确保该文件存在，否则启动会报错。

检查点会校验动作集合元数据、态势版本和输入宽度，网络权重加载还要求 `hidden_size` 等结构参数与训练时一致。动作集合、特征宽度或网络结构改变后，不应强行加载旧模型。比赛时还必须由 UE 下发 `training=0`；它与 `load_model=True` 分别负责“禁止训练”和“加载已有权重”，缺一不可。

## 7.8 模板 DQN 的精简动作空间

红蓝 DQN 模板均使用固定的八个动作槽：Idle、四个水平移动方向、移动到按 `team_index` 分配的任务目标、攻击当前 Agent 局部感知中的最近敌人、为非士兵无人装备切换到最近的可用上级。攻击目标和上下级 UID 在动作被选中时按当前帧解析；上级候选为本方存活士兵和初始 Commander，网络输出宽度不会随兵种或可见敌人数变化。

| 动作索引 | 动作 |
|---:|---|
| 0 | Idle |
| 1–4 | `+X`、`+Y`、`-X`、`-Y` 四个移动方向 |
| 5 | 移动到当前分配目标 |
| 6 | 攻击当前 Agent 局部感知中的最近敌人 |
| 7 | 为非士兵无人装备切换到最近可用上级 |

对应模型输入固定为 25 维：10 维自身信息、5 维分配目标、6 维最近局部敌人、3 维上级切换状态和 1 维当前步数。自身信息不枚举固定 UE 兵种类名，而由存活、生命值、速度、最大速度、武器冷却、攻击范围、警戒范围和感知范围组成；新增兵种只要提供这些通用字段即可进入同一网络，不需要修改输入宽度。示例不输入全部友军、全部敌人或全部指挥所，避免无关特征和可变长集合增加训练难度。数值字段和相对位置、相对距离均使用原始工程量，不在框架或示例中额外缩放；选手可根据自己的算法自行预处理。

25 维输入的固定顺序如下：

| 输入索引 | 字段 |
|---:|---|
| 0 | 本实体是否存活 |
| 1 | 本实体当前生命值 |
| 2–4 | 本实体原始速度 x、y、z |
| 5 | 本实体最大移动速度 |
| 6 | 本实体武器冷却 |
| 7–9 | 本实体攻击、警戒、感知范围 |
| 10 | 是否存在分配目标 |
| 11–13 | 目标相对位置 x、y、z |
| 14 | 目标相对距离 |
| 15 | 是否存在局部可见敌人 |
| 16 | 最近局部敌人当前生命值 |
| 17–19 | 最近局部敌人相对位置 x、y、z |
| 20 | 最近局部敌人相对距离 |
| 21 | 是否存在可用上级候选 |
| 22 | 当前是否需要切换到该候选上级 |
| 23 | 当前通信链路是否正常 |
| 24 | 当前回合步数 |

缺失的可选数值、目标或敌人使用 0 填充；存在性标志用于区分“值为 0”和“对象不存在”。

该动作集合只保留基础交互闭环。选手需要增加动作时，应修改自己的 `ActionSetDefinition`，同步升级动作集合版本并重新训练模型。
