# 9. 发布接口与开发约束

## 9.1 选手稳定接口

推荐选手只依赖：

- `cssim.algorithms`：`RuleAlgorithm`、`ReinforcementAlgorithm`、`AlgorithmContext`、`ActionSetDefinition`、`LearningTransition`；
- `cssim.environment`：`TeamState` 及公开的 `Entity`、`KeyObject`；
- `cssim.protocol`：`Action`、`ChangeParentAction`、`DiscreteAction`、`RLActionSet` 和方向常量；
- 自己队伍目录内的算法和模型文件。

`runtime`、`transport` 和内部 `SimulationState` 属于框架实现，不是选手扩展点。

## 9.2 必须保持的约束

- TaskConfig、AlgTemplate、TeamAlg 的目录约定不变。
- 使用 gRPC，不提供旧 TCP 路径。
- `num_worker_threads=1`，单环境、单事件循环。
- 每个实体每帧只选择一个逻辑动作，禁止动作组合。
- 返回顺序必须与 `state.agents` 一致。
- 不访问未通过 `TeamState` 暴露的敌方全量信息。
- 动态 UID 不跨回合缓存。
- 模型动作集合或特征结构变化后重新训练。

## 9.3 框架保证与选手责任

框架保证：阵营数据隔离、本回合内本方 `state.agents` 动作行稳定、动作对象校验、执行者 UID 编码、特殊动作阵营/存活校验、转移生命周期、训练/比赛标志和结构化日志。这里的动作行稳定是 Python 算法接口约定，不表示 UE 要求 `StringActions` 复刻 `propertyArr` 的数组顺序。

选手负责：战术有效性、实体与动作适配、自定义奖励、动作 mask、网络结构、训练稳定性、检查点策略以及是否使用队伍共享或单体局部感知。

## 9.4 发布验收

1. 使用目标 CPU 环境运行 `python -m compileall -q .`。
2. 使用开发环境运行 `python -m pytest tests -q`。
3. 规则模式红蓝至少连续运行三回合。
4. 强化学习训练模式和加载模型比赛模式各运行一次。
5. DEBUG 检查普通动作字符串和 `ChangeParentAction` 的单动作语义。
6. INFO 长回合检查日志体积和模型保存。
7. 多指挥所场景检查目标集合、目标分配和终局。

对外发布时以本目录 1–9 号文档、UE JSON 协议附录和当前代码为依据；附录中的具体实体数量、UID 和结果只代表注明日期的样本回合。

## 9.5 哪些代码可以修改

| 区域 | 选手是否建议修改 | 原因 |
|---|---|---|
| `TeamAlg/<自己的队伍ID>/Algorithm` | 是 | 规则、态势、动作集合、网络和训练实现 |
| 自己队伍的模型目录 | 是 | 保存或加载检查点；模板路径为 `TrainLogs/dqn_model.pt` |
| `AlgTemplate` | 平台维护者修改 | 决定以后新建队伍得到的初始案例 |
| `TaskConfig` | 通常否 | UE 自动生成并覆盖 |
| `cssim/algorithms`、`environment`、`protocol` | 通常否 | 发布框架公共接口和统一语义 |
| `cssim/runtime`、`transport` | 否 | 调度和底层通信实现 |

选手确有研究需要时可以阅读框架代码，但比赛算法不应通过导入内部 `SimulationState`、运行器或 gRPC 客户端绕过安全视图和动作接口。

## 9.6 算法提交目录最低要求

```text
TeamAlg/<队伍ID>/
├─ __init__.py
├─ model.jsonc
├─ Algorithm/
│  ├─ __init__.py
│  ├─ RLAgentAlgorithm.py
│  └─ 规则或强化学习实现文件
└─ TrainLogs/                    使用模板 DQN 加载模型时需要
   └─ dqn_model.pt
```

入口必须能够通过 TaskConfig 中的模块路径导入，并最终返回 `cssim.algorithms.Algorithm` 的实例。选手在自己的 `RLAgentAlgorithm.py` 的 `AlgorithmConfig` 中配置算法模式和模型加载；比赛使用模板 DQN 时应设置 `mode="reinforcement_learning"`、`load_model=True` 并提交对应检查点。模型文件可以按算法需要增加，但不应把 Python 环境、普通运行日志、缓存和训练数据集整体放入提交目录。

## 9.7 接口兼容性规则

- 修改 `ActionSetDefinition.define()` 的顺序、数量、名称或参数语义时，升级动作集合 version 并重新训练。
- 修改模型输入特征宽度、集合含义或归一化时，旧检查点不再兼容。
- 新增 UE 字段时，优先在自定义 observation 中显式使用；只有被证明为通用且安全的字段才进入框架公共对象。
- 新增特殊 UE 接口时，应封装成动作对象和独立执行器，并保持一个 Agent 每帧一个逻辑动作。
- 不把请求侧 protobuf 字段擅自假定为 UE 必定回显的响应字段；prepare 回包以通道、串行请求关系和 JSON 必需内容为准。
- 不把 UE 当前 bug 的规避逻辑写成永久协议语义。

## 9.8 发布包清理

对外包应保留 `main.py`、`cssim`、AlgTemplate、必要 TeamAlg 兜底、TaskConfig 结构、发布文档和环境依赖说明。应移除运行日志、模型临时文件、`__pycache__`、`.pytest_cache`、个人测试队伍和内部历史资料。

## 9.9 最终验收结果如何判定

自动化测试用于验证 Python 接口、编组、隔离、动作编码和训练数据流；真实 UE 联调用于确认 Python 请求能够按现有协议发送并收到有效回包。建议形成一张验收表，分别记录：

- 规则红蓝连续多回合是否结束；
- 强化学习训练是否产生经验和参数更新；
- 比赛模式是否只加载和推理；
- 比赛队伍自己的 `AlgorithmConfig` 是否启用模型加载，`TrainLogs/dqn_model.pt` 是否存在且与当前网络和动作集合兼容；
- 普通动作和 `ChangeParentAction` 是否携带正确的本回合 UID 并按协议发出；
- 多指挥所是否全部进入态势并参与策略；
- 新回合 UID 更新后动作是否仍指向正确对象；
- DEBUG 与 INFO 日志是否符合用途和体积预期。

Python 发布验收以“不抛出框架错误、动作格式和动态 UID 正确、回包可解析、回合与训练流程完整”为准。动作被 UE 接收后是否产生预期物理效果属于 UE 实现验收，不作为 Python 框架错误判定。
